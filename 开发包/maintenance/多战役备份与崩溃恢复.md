# 多战役备份与崩溃恢复

程序包内的管理员入口为 `主程序/manage_installation.py`；开发包入口只转发同一个实现。备份为可搬移的私有目录，目录和文件分别使用 0700 / 0600 权限，含账号认证数据库，不能公开分享。

## 操作

所有 DM 先保存并关闭页面，正常关闭整套服务及房间进程。工具不会自动结束服务，也不会关闭 Tunnel。

```sh
python3 程序包/主程序/manage_installation.py create --root 程序包 --output 私人备份/全部战役-新编号
python3 程序包/主程序/manage_installation.py verify --backup 私人备份/全部战役-新编号
python3 程序包/主程序/manage_installation.py restore --root 程序包 --backup 私人备份/全部战役-新编号 --expected-manifest-hash 校验结果中的manifestHash
python3 程序包/主程序/manage_installation.py recover --root 程序包
```

`verify` 不修改权威数据，可在服务运行期间核验独立备份。其余三个命令获得安装级独占锁，并获得中央服务、每个已物化空间的原有服务锁；新主服务和房间进程在整个生命周期内持共享安装锁，阻止维护期间的新启动。旧版本服务仍会被原有工作区锁识别并拒绝归档。

备份包含中央邮箱账号数据库、角色与独立背包及素材、全部 `战役空间/<roomId>`、检查点和 `历史归档`。旧同级模块安装的根通用包、战役包、玩家包也保持兼容。活动 SQLite 从含已提交 WAL 的私有只读快照生成独立数据库；已经冻结的历史归档逐字节复制，包括其历史辅助文件，以保留归档自己的完整性清单。验证文件清单、目录清单、SHA256、数据库完整性、外键、原始资产尺寸与哈希、空间身份与成员关系。只有数据库记录但未访问的空间在清单中标为 `materialized=false`，不会被误判为损坏。已物化空间没有数据库记录、标记或协调库时拒绝备份。

机器发信密钥和 Tunnel 配置所在的 `运行数据/联机`，以及当前安装的 `联机设置.json`、`邮箱账号设置.json` 不读取、不进入备份，恢复保留目标机器现有配置。中央邮箱账号数据库和身份凭证照常备份。活动目录的旧备份、安装级备份、恢复任务、锁文件及临时房间前端副本不递归进入备份；历史归档内部保持原样。旧单工作区备份格式只用于隔离恢复，安装级命令拒绝把旧格式当作全部空间的备份。

恢复先验证输入备份，再复制并验证私有恢复副本，并创建通过同样校验的恢复前备份。替换每个目录前写入恢复事务；普通异常自动回滚。恢复进程若被强制结束，事务保留，新服务拒绝启动。运行 `recover` 验证恢复前备份后回滚，再启动服务；暂存的原目录缺失时从已校验的恢复前备份恢复，不能证明恢复完整时保留事务并报错。恢复前备份留在 `运行数据/安装级恢复任务/<任务>/恢复前备份`。恢复成功更新工作区代次，旧账号会话失效，原已验证账号仍可重新密码登录。

目前工具接受第4版同级模块安装或中央账号房间安装，最大64 GiB、500000个文件及目录条目；采用停服备份。账号房间模式的中央目录不要求游戏协调库，但每个已物化房间仍必须完整。恢复前的当前安装也必须能生成完整回滚备份，损坏到无法校验的安装需保留原始目录另行安排修复，工具不会强行覆盖。跨应用版本还需匹配协议版本，工具不替代格式迁移。

## 房间检查点

房间状态、玩家动作、日志、改变 BGM 的 GM 动作，以及收入小库产生的地图绑定，在变更请求的成功状态行发出前原子写入并 fsync 私有检查点；已确认操作不留定时检查点的丢失窗口。SSE 广播本身不是落盘确认；应以对应请求的成功响应为准。未收到成功响应的请求仍可能处于未完成状态，需要按原请求标识重试。动作幂等回执保留最近2000项，战役切换会清理；超出窗口不承诺去重。无变化的认证、查询和心跳不反复写入大状态。正式存档保存、模块导入和账号业务的成功响应确认各自已落盘的业务结果，不表示旧运行状态已写入检查点。

检查点带空间身份、协议版本、正式存储的提交版本和当前战役文件哈希。SQLite 提交版本由触发器更新，包含 WAL 中的已提交变化。正式文件按文件内不可变战役 ID 定位，支持带名称目录，拒绝同身份多目录；保留缺少显式身份的历史裸 ID 目录。每次检查一层目录与文件元数据，只有内容变化的正式文件重新读取并缓存身份及哈希，不扫描资源目录。SIGKILL 后能恢复匹配的公开状态、动作序号与幂等回执，玩家需重新建立会话。

主控台从 `read-campaign.sourceHash` 或成功 `write-campaign.hash` 保存已读取/保存的正式来源，在发布状态时附内部 `_formalSourceHash`，此字段不发给玩家。正式存档更新后，旧来源的运行变更在修改前返回409；重新读取并发布当前来源后恢复正常。先发布草稿、再正式保存的操作仍会收到保存成功的新哈希，随后重新发布即可接续。当前正式哈希已证明时，独立玩家背包等数据库变化可正常更新检查点，不要求无关的重新发布。跨空间、正式版本不匹配、缺少来源证明的旧检查点（包括旧 schema2）保留至 `运行数据/检查点保留`，不自动恢复；协议不兼容时保留检查点并拒绝启动，等待迁移。

开发测试全部使用临时目录和随机本机端口，覆盖两次 SIGKILL、动作回执恢复、持久化失败不返回成功、旧/跨空间检查点保护、活跃进程拒绝归档、篡改与穿越、恢复中断回滚，以及恢复后的会话失效和重新登录。

# 棋子立绘制作流程

## 标准流程

1. 打开 `棋子库.html`，点击顶部「🎨 立绘工作台」。
2. 优先选择带 `○` 的缺图棋子。工作台会根据棋子分类自动选择「人物／生物／坐骑／物件／法术造物」，判断不合适时可手动改选。
3. 在「外观补充」中只写决定辨识度的内容：体型与轮廓、主色、材质、主要装备或功能部件、姿态，以及 1—2 个必须保留的特征。
4. 复制工作台生成的提示词，交给 Codex 或图像模型绘制。初次生成只做一个主体、一个动作和一个视觉焦点；结果偏离时先修正外观补充或类型，不在提示词末尾反复堆叠形容词。
5. 在正常尺寸检查造型与结构，再使用圆形裁切预览将图片缩小到 192×192 和 64×64 检查可读性；不合格则重新生成或修改后再入库。
6. 第一次使用时点「📂 绑定棋子库文件夹」，选择项目中的整个 `棋子库` 文件夹。
7. 成图后点「⬆ 导入成图」。程序会自动绑定棋子，并把原图归档到 `立绘/<一级分类>/<二级分类>/<棋子名>.<扩展名>`。
8. 新增或替换正式立绘后，运行 `python3 asset/棋子库/生成显示缓存.py` 生成 192/512px 显示缓存。
9. 回到主控台点棋子库「⟳ 同步」，打开顶部「高清」检查地图、骑手、详情卡和玩家页。浏览器内嵌立绘缓存缺失时再使用「重建高清缓存」。

## 类型判定

工作台按下列优先级自动选择模板，类型下拉框始终可以手动覆盖：

| 数据特征 | 生成类型 |
| --- | --- |
| 一级分类为 `坐骑` | 坐骑 |
| 一级分类为 `物件` | 物件 |
| 一级分类为 `法术造物` | 法术造物 |
| 一级分类为 `玩家`、`NPC`，或棋子类型为玩家、NPC | 人物 |
| 其余类型，包括怪物与魔宠 | 生物 |

## 统一立绘规格

- 画布：1:1 方形，建议至少 1024×1024。
- 圆形安全区：输出仍为方形，但最终显示为圆形棋子。以画布中心、直径约占画布 86% 的无形圆形作为构图安全区；头顶、底部、四肢、角、翼、尾、武器、功能部件和关键特效都必须完整落在安全区内。
- 安全区用途：86% 圆只负责约束构图，不是画面元素。系统会将项目路径立绘放大约 116.3% 后放入圆形容器，正好让 86% 安全区覆盖棋子；因此不能把圆形边缘实际画进成图。
- 背景：整张方形画布连续铺满低信息量的浅暖旧纸色或柔和中性底，并与主体形成清楚的明暗或冷暖对比。不要画出圆形底板、圆形边界、内外分区、外环、徽章框或场景化环境。
- 风格：西幻规则书插画质感、厚涂写实、材质明确。高分辨率细节必须服从整体轮廓，不能依靠微小饰品或密集纹样承担主要辨识功能。
- 小尺寸可读性：以最终圆形裁切效果检查；192×192 时轮廓、姿态和主要装备边界清楚，64×64 时仍能辨认主体类别、朝向以及 1—2 个核心特征。优先使用清楚剪影、大色块、明确明暗层级和单一色彩焦点。
- 通用限制：不要文字、边框、UI、签名、水印、彩色装饰环、多格排版、无关角色或未要求的叙事元素。
- 命名：默认使用棋子名称。绑定文件夹后由程序自动命名和归档，不需要手工整理。

## 五类主体规则

### 人物

- 使用单个人物全身立绘，正面或轻微四分之三视角。
- 以面部、头肩轮廓、主武器或标志性装备作为主要识别点，动作简洁有力。
- 只出现一名人物；手部、武器与穿戴关系必须合理；大面积披风或特效不能吞没身体轮廓。

### 生物

- 使用能说明身体结构的正面或四分之三视角，突出物种轮廓、头部、肢体比例以及角、翼、尾等关键特征。
- 只出现一个生物；解剖结构与着地关系清楚，不能重复肢体。
- 翅膀、尾巴、角和主要武器必须完整保留在画面内。

### 坐骑

- 单独展示一匹完整坐骑，优先使用侧前方四分之三视角，姿态稳定并具有前进感。
- 清楚表现头部、躯干、四肢、承载位置以及符合身体结构的鞍具或缰具。
- 不出现骑手或额外角色；扬尘、火焰、翅膀等不能遮住腿部与承载位置。

### 物件

- 单件物品完整展示，优先使用略微俯视的三分之四视角。
- 通过外轮廓、材质分区和功能部件说明物件是什么、如何使用；可以保留轻微接触阴影帮助辨认体积。
- 不出现人物、手、容器外的额外道具或完整场景；复杂装饰不能掩盖功能结构。

### 法术造物

- 单独展示一个法术造物，以稳定主体轮廓、一个核心形态和一种主要能量效果表达法术性质。
- 不出现施法者、施法者的身体部位或额外目标。
- 粒子、烟雾、光晕和符文只能辅助主体，不能覆盖轮廓；符文不得形成可读文字。

## 入库前检查

- 主体数量正确，并符合所选生成类型。
- 主体没有被裁切，没有多余肢体或结构错误。
- 所有关键辨识信息都位于居中的 86% 圆形安全区内。
- 背景连续铺满方形画布，没有画出安全区边界、圆形底板、装饰环、边框、文字、UI、签名或水印。
- 最终圆形裁切为 192×192 时，姿态、主装备和功能部件边界清楚。
- 最终圆形裁切为 64×64 时，能立即辨认主体类别，并能指出 1—2 个核心特征。
- 文件名、棋子名称和目标分类一致，再执行导入与显示缓存生成。

## 储存与归档规则

- 当前立绘：`asset/棋子库/立绘/<一级分类>/<二级分类>/<棋子名>.png`。
- 可再生显示缓存：`asset/棋子库/显示缓存/{192,512}/<同一分类>/<棋子名>.webp`。它们用于运行时显示，不是第二份立绘归档；丢失后可用 `生成显示缓存.py` 重建。
- 路径只保存在每条棋子预设的 `iconImgPath` 中：正式数据以 `存档/棋子库/棋子库.json` 为准，`默认预设.js` 只供首次启动。移动或替换立绘时请通过棋子库重新导入，避免手工维护两份路径。
- 项目不再保留旧立绘归档；替换当前立绘前如需保留版本，请使用 Git 提交或另行备份到项目外。

## 高清数据规则

- 项目原图：只用于编辑、重建显示缓存，以及缓存文件缺失时的自动后备。
- 2048px：保存在当前浏览器的原图缓存，方便编辑和重新生成显示版本。
- 512px：主控台放大或显示大体型棋子时自动使用，玩家页和详情预览也使用此档。
- 192px：主控台普通缩放和棋子库列表使用；高分屏小棋子仍清楚，同时显著降低解码与显存开销。

顶部「高清」关闭时固定使用 192px；开启时会根据棋子实际屏幕尺寸在 192/512px 之间切换，不会一次加载全部原图。

如果没有绑定文件夹，导入仍然有效，但只会保存浏览器缓存和内嵌高清后备；为了换电脑和长期保存，推荐始终绑定项目中的 `棋子库` 文件夹。
